# Arcade World operating routes

These routes are execution notes for the existing scheduled tasks. The scheduled task prompts remain in ChatGPT; this file does not schedule them. Read `EDITORIAL_PLAYBOOK.md` for the editorial standard and `ANALYTICS.md` for the collection model.

## Sunday: measurement, learning, three hypotheses

1. Check current Codex capacity when available. Do not use resets. Run `npm run analytics:weekly` from the project root. Read `analytics/weekly/latest-data.json` first; its `ga4_status`, `search_console_status`, and snapshot dates say whether the current API attempt succeeded. Read the linked 7-day and 28-day summaries and their underlying page/landing/channel/query/event reports only where useful.
2. Read the prior `analytics/weekly/latest.md` before replacing it. Compare article performance at 7 and 28 days, with publishing dates and sufficient sample size in mind. For each apparent winner or loser, distinguish the observation (e.g. impressions, clicks, CTR, article views, engaged sessions) from a plausible explanation (topic, query intent, timing, headline, referrer, page experience). Do not present correlation as proof.
3. If a Google API call fails, keep its last valid snapshot **with its original date** and mark it stale; do not call the weekly report fresh. Search Console has its own lag and only describes Google Search, while GA4 covers measurable site traffic. Neither can identify every visitor or recover lost attribution.
4. Scan current gaming interest using dated Google Trends/News results, official platform/publisher/developer notices, and public player discussion only as interest signals. Record query, timestamp and timezone, market, two distinct dated interest signals with URLs, age, saturation, shelf life, player impact, primary source, and independent verification needed. Discard rumors, duplicates, weak player impact, and saturated topics without a specific angle.
5. Replace `analytics/weekly/latest.md` with the 7/28-day findings, limitations, lessons tied to evidence, rejected topics, and Tuesday/Thursday/Saturday hypotheses. Each hypothesis has the player's question, specific editorial value, saturation risk, sources to verify and realistic visual direction. Each publication day must revalidate within 48 hours and may skip.

## Tuesday / Thursday / Saturday: at most one article

1. Read `EDITORIAL_PLAYBOOK.md`, current capacity, `analytics/weekly/latest.md` only if under eight days old, and the existing `content/articles/` slugs and `data/blog-data.js`. If the five-hour remaining capacity is below 35%, weekly remaining below 25%, or capacity data required by the task is unavailable, skip before costly research/image work. Do not consume resets.
2. Recheck the Sunday candidate and recent interest (within 48 hours). Require two dated, distinct interest signals; confirm the facts with a primary official source and a reliable independent source. Trends and player discussion do not confirm facts. Select an angle that changes a player decision; skip weak, duplicated or saturated stories. Do not treat a target of three posts as a quota.
3. Create one `draft` JSON under `content/articles/`. Write factual English copy using JUEGO, accurate dates/timezones, useful sections, sources, and a clear separation of official announcement, independent confirmation and editorial interpretation. If needed, generate one original 16:9 editorial illustration, label it as AI-generated, and provide descriptive alt text and credit. Never pass generated art off as documentary photography.
4. Verify details, links, accessibility and image rights. Set `published` only when complete. Run `npm run content:build`, `npm run test:launcher`, and `npm run build:web`. Run `npm run test:analytics` when measurement code changed. Check the article page, blog index, feed, XML sitemaps, and referenced local assets. On failure, keep draft and do not deploy.
5. Deploy with `npm run deploy:web` (Firebase Hosting project `arcade-world`; this command rebuilds `site-dist/`). Check the live article URL, title, image, `analytics-config.js`, and `analytics.js` over HTTP. Report deployment only after live checks pass. GitHub is not part of the serving path.

## Working tree and API access

- Before writes, inspect `git status --short` and relevant diffs. Existing changes are allowed if they do not conflict with this task. Do not revert them or silently include them in a release; `build-static.ps1` collects current public files, so inspect their effect on `site-dist/` before deploying.
- Weekly API configuration is local and ignored by Git: `analytics-local.json`, `credentials/`, Python packages in `scripts/requirements-analytics.txt`. A successful `npm run analytics:weekly` reports availability in `latest-data.json`; the presence of old report files alone is not evidence of live access.
- A connector can answer questions in chat only if installed and authorized for that service. This project's default is official Google APIs; a third-party GA4 connector requires a new explicit user choice. Search Console needs independent access. If the current sandbox blocks network/DNS, do not retry indefinitely or ask for a browser export; give the exact terminal/API handoff.
- Attribution cannot be guaranteed at 100%: stripped referrers, privacy settings, apps and non-human requests can show as Direct or remain unmeasured. Diagnose with GA4 landing page, source/medium, campaign parameters and Search Console clicks/impressions; never relabel unknown traffic as known.
